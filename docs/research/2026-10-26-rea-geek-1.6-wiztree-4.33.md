## 2. Geek Uninstaller 1.6 — observed internals

### 2.1 Architecture

MSVC RTTI and logging strings expose the module split:

- Inventory: `CUninstaller`, `CUninstallRegData`, `CUninstallItem`, `CUninstallCache`, `CUninstallItemMetroApp`, `MetroAppsLoader`, `MetroAppIcon`.
- Derived data: `CFindIconJob`, `CFindSizeJob`, `CInstallLocationFinder`.
- Exit flow: `CUninstallProcess`, `ProcessHelpers::ProcessList`, `getRunningProcessesStartedAfter`.
- Leftover wizard: `CScannerAbstract`, `CScannerNormal`, `CScannerMSI`, `CScannerMetro`, `CScannerCustomRules`, `CWizardScanner`, `CWizardTreeCtrl`.
- Installer/Uninstaller: `Uninstaller.cpp`, `UninstallRegData.cpp`, `InstallLocationFinder.cpp`, `FindIconJob.cpp`, `FindSizeJob.cpp`, `Cache.cpp`, `MetroAppsLoader.cpp`, `WizardScanner.cpp`, `WizardScannerMSI.cpp`, `WizardScannerNormal.cpp`, `WizardTreeCtrl.cpp` (source paths retained in the PE).

The reduced-analyzer Ghidra overview observed **16,776 procedures** and **4,439 defined strings** (`ev_597a3ea861ccffd2dbdde1f7c573f14ed940ac6614e583338714f5c7994378e6`). The UI is an MSVC/ATL-MFC application using statically linked Codejock XTP controls (`CXTPToolBar`, `CXTPTaskDialog`, `CXTPShortcutManager`), GDI/GDI+, and PNG resources. Imported APIs include `Process32FirstW/NextW`, `QueryFullProcessImageNameW`, `GetProcessTimes`, `WaitForMultipleObjects`, `WaitForInputIdle`, `TerminateProcess`, `SuspendThread`, `MoveFileExW`, `ShellExecuteExW`, `EnumResourceLanguagesW`, `RegEnumKeyExW`, `RegEnumValueW`, and MFC/ATL runtime symbols.

### 2.2 Inventory and derived-data cache

Observed from a live local runtime artifact (`%APPDATA%\Geek Uninstaller`):

- `prefs.xml`: gzip-independent XML `<PortableProgramData version="2">` storing `ColorScheme`, `InitialSortOrder`, `InitialSortParam`, `Interface_Language`, `Window_Maximized`, `Window_Rect`, and four column widths.
- `cache.dat`: 10,400 B gzip stream → 63,560 B XML `<UninstallCache version="3">`.
- Each `<CacheItem>` has exactly `key`, `location`, `iconPath`, `iconIndex`, `size`.
- Sentinels: `location="-"`, `iconPath="-"`; unknown size is `4294967295` (`0xFFFFFFFF`).
- The inspected cache had 293 items, 30 unknown sizes, 140 missing locations, and 133 missing icons.
- `IconsCache/` stores extracted icons.

Inference: `cache.dat` is a derived-field cache keyed by an uninstall-entry key (display name or product GUID), not a full inventory snapshot: it contains no display publisher/version/date and no enumeration timestamp. `CUninstaller::LoadCachedData` likely merges cached location/icon/size into freshly enumerated entries; `CUninstallCache::Save` rewrites them. The UI exposes `Clear cache`.

The cache schema and settings file are runtime observations from the shipped executable on this host, not strings recovered only from the PE. Hashes: cache.dat `5c446165…e8172a0`, cache.xml `4aa8b70e…b85137`, prefs.xml `3f6c33ca…79a078`.

### 2.3 Registry and Store enumeration

#### 2.3.1 Icon derivation (2026-10-27 follow-up)

Geek's icon finder at `0x42fc55` (`ev_1da50583b17bc3e0e99bd3849d3c0c7d6509828f93275f0844964641e9f8e628`) walks DisplayIcon → Start Menu shortcut → InstallLocation → UninstallString → Windows Installer, then caches either the icon path/index or an empty sentinel. Its Store loader uses `AppxManifest.xml` plus `MetroAppIcon::findLogoFile / findLogoToDraw / searchAndCacheIcon`.

PurgeKit's current resolver mirrors and extends that order:

1. Expand `%ENV%` variables and strip icon indices from `DisplayIcon`.
2. Start Menu shortcut `IconLocation`, then shortcut target (captured in one PowerShell pass and matched conservatively).
3. Uninstaller executable.
4. Executables in the install folder (`bin`, `cmd`) scored by app-name words.
5. Executables found through `PATH`.
6. Portable apps use their discovered executable; CLI/toolchain rows use their manager runtime icon.
7. Store apps use manifest logos, then the manifest application executable, then a bounded package walk, then a WindowsApps-only shell app-link fallback for stub/streamed packages.
8. The derived-field cache stores resolved paths/base64 and invalidates them with a v3 registry + binary-stamp fingerprint.

Host measurement after this change: **132 of 133 inventory rows have a logo**. The remaining `vs_CoreEditorFonts` entry is a font component with no application icon; Registry 55/56, Store 66/66, CLI 8/8, Toolchain 2/2, Portable 1/1.

Strings show the expected ARP roots plus additional heuristics:

- `HKCU`/`HKLM` `SOFTWARE\Microsoft\Windows\CurrentVersion\Uninstall` and both `Wow6432Node` views.
- `SOFTWARE\Microsoft\Windows\CurrentVersion\Installer\Folders` and `Installer\UserData\<SID>\Products\<ProductCode>` (MSI install-root discovery).
- `Software\Microsoft\Windows\CurrentVersion\App Paths`.
- `ApplicationView`, `AppSync\DEH`, `AppContainer\Mappings`, `AppModel\SystemAppData`, `Local Settings\...\AppModel\Repository\Families`.
- `Component Based Servicing`, `SideBySide` (Windows Update/system-entry context).
- Policy roots (`Policies\Explorer`, `Policies\Network`, `Policies\Comdlg32`) appear in strings but their role is not established by static evidence.
- Values consumed: `DisplayName`, `DisplayIcon`, `DisplayVersion`, `InstallLocation`, `InstallDate`, `UninstallString`, `QuietUninstallString`, `ModifyPath`, `SystemComponent`, `ParentKeyName`, `ReleaseType`, `WindowsInstaller`, `EstimatedSize`, `Hidden`, `NoModify`.

Store apps are enumerated by `MetroAppsLoader::loadMetroApps`; icons use `AppxManifest.xml` and `MetroAppIcon::findLogoFile/findLogoToDraw/searchAndCacheIcon`; removal is delegated to `powershell.exe Remove-AppxPackage %s`.

Command-line switches observed in strings: `--uninstall-app-id=`, `/store_apps`, `/select, "%s"`, `/restart`, `/O /T "%s"`, `/aplank`. Separate PDB names (`geek.pdb`, `geek64.pdb`, `geek-arm64.pdb`) show 32-bit, 64-bit and ARM64 builds; only the x86 binary is in the supplied archive.

### 2.4 Install-location inference

`CInstallLocationFinder` exposes four strategies: `FindInstallLocation`, `FindByDisplayName`, `FindByUninstallString`, `FindProgramDirByDisplayName`. Logging strings include:

- `GetInstallLocationFromPathLevinshtein ({})` and `returned {}` — Levenshtein similarity is used between path components and the application name.
- `False positive InstallLocation found {}` — inferred paths are validated before acceptance.
- `Found install location in Local AppData Programs: {}`.
- `- FindAppDataFolders done`, `- FindAppDataRegFolder done`.
- Shortcut searches: Start Menu trees, desktop shortcuts, Quick Launch and `User Pinned\TaskBar`.
- MSI: `Found MSI product key {} for {}`, `Setting manually MSI /I path for {}`, `Setting manually MSI /X path for {}`.

The exact scoring/threshold logic remains a decompilation target; static evidence establishes the inputs, not the weighting.

### 2.5 Uninstall execution and process handling

`CUninstallProcess::Uninstall_Thread` and `CUninstallProcess::WaitForProcessAndChildren` are explicit module names. Imports include Toolhelp (`Process32FirstW/NextW`), `OpenProcess`, `GetProcessTimes`, `QueryFullProcessImageNameW`, `WaitForMultipleObjects`, `WaitForInputIdle`, `TerminateProcess`, `SuspendThread`, `ResumeThread`, `IsWow64Process`, and `K32EnumProcessModules`.

Observed implications:

- The class is named “WaitForProcessAndChildren”; its decompiled body waits on a process handle plus an event and can terminate the process. Child enumeration is not established by that body, even though Toolhelp APIs are imported elsewhere.
- `ProcessHelpers::ProcessList::getRunningProcessesStartedAfter(FILETIME)` enumerates processes newer than a baseline time. Its call site is unresolved; it is not proof of a general “stop running apps” feature.
- The decompiled `WaitForProcessAndChildren` waits on one process handle plus one event. Child-process enumeration may occur elsewhere; the function name alone is not evidence that the whole tree is awaited.
- Reboot-queued deletion is used: strings `ERROR_SHARING_VIOLATION, the folder will be deleted on the next system restart` and `ERROR_ACCESS_DENIED, the file will be deleted on the next system restart`; `MoveFileExW` is imported.
- The UI offers Uninstall, Modify, Force Removal, Batch Force Removal, Remove Entry, Batch Remove Entries, and Registry/Install Folder/Website/Store/Browse Source shortcuts.

## 3. WizTree 4.33 — observed internals

### 3.1 Architecture

Delphi RTTI and strings identify the main units/classes:

- Main form: `TfrmWizTreeMain`, actions such as `actScan`, `actAutoScan`, `actSelectMFT`, `actExport`, `actSelectCSV`, `actShowTreemap`, `actShowAllocatedSize`, `actRunAsAdmin`, `actRestartAsAdmin`.
- NTFS/MFT: unit `myntfs`, `TMFT_RECORD`/`PMFT_RECORD`, `TNTFS_FILES`, `TNTFS_VOLUME_DATA_BUFFER`, `TNTFS_ProcessThread`, `TMFTThread`, `TMFT_EXTENTS`.
- Data view: `TDUPFILES`, `TDUPFILES`, `TFileTypeItem(s)`, file-list and tree-view abstractions.
- Export: `TfrmExportTreemap`, `exporttreemap.pas`, `SaveToCSVFile`, `OpenDialogCSV`, `TCSVClipboardFormat`.
- Config: JCL registry storage, `LoadAdminSettingsFromRegistry` / `SaveAdminSettingsToRegistry`, `ConfigOverride`.

The binary is a VCL application using VirtualTreeView (`vstFiles`, `TVT*`), JVCL helpers, VCL styles, GDI/Direct2D painting, and WinHTTP-based update checks. Its RTTI exposes 122 `act*` action names, from `actScan` and `actSelectMFT` to `actDeleteRecycle`, `actDeleteNoRecycle`, `actExportVisible`, `actProperties`, `actSetColors`, and `actToggleHeader`. It exports only Delphi `__dbk_fcall_wrapper`/`dbkFCallWrapperAddr`; ordinary symbols are stripped. The reduced-analyzer Ghidra overview observed **35,969 procedures** and **14,454 defined strings** (`ev_e39bf6200b6f5adf74d2ae42d19f043f403eb390c083b5d3b46eeda55b46732c`). `.pdata` contains roughly the same function count, which is why the full decompiler-switch pass exceeded REA's default 330 s startup deadline.

### 3.2 MFT fast path

Observed strings establish the primitives without execution:

- `myntfs`, `TMFT_RECORD`, `PMFT_RECORD`, `TMFT_EXTENTS`, `GetMFTRecord`, `GetMFTExtents`, `ProcessMFTRecords`, `NumMFTRecords`, `MFTRoot`, `MftValidDataLength`, `MftZoneStart/End`, `FMFT_UPCASE`, `upcase.dat`.
- `FSCTL_GET_RETRIEVAL_POINTERS, StartingVCN= `; `NtFsControlFile`; `TNTFS_VOLUME_DATA_BUFFER`.
- `FullScanNTFSIfPossible`, `FullNTFSScanForFolder`, `IncludeNTFSSpecialFiles`, `UseMFTExtents`, `FMFTExtentsAvailable`.
- `Dumping MFT file, please wait...`, `MFT data dump complete.`, `MFT data dumped to file`, `LoadMFTDevices`, `Select MFT`, `DoLoadFromMFTSource`, `MFT Dump`, `All Files`.
- Errors: `No MFT root found!`, `Please restart WizTree as Administrator to dump the MFT file`, `Please select an NTFS formatted drive.`, `Could not decode first MFT Upcase record!`.

Inference (corroborated by the decompiled sequence in §3.3): WizTree opens the volume, reads `$MFT`, resolves its fragmentation through `FSCTL_GET_RETRIEVAL_POINTERS`, loads the upcase table from MFT record 10 for case-insensitive name comparison, builds a record→children map, and derives logical/allocated sizes. Hardlink policy and compression/sparse handling still need dedicated decompilation; the current evidence does not prove them.

Non-NTFS/network/USB/folder scans use `TSlowScanThread` (“Slow scan”), matching the about text: “As of version 2.0, WizTree can now also scan non NTFS hard drives, network drives, USB drives, and individual directories.”

## 5. Inferences, unknowns, and limits

- No target was executed by this analysis. Geek's cache/prefs and WizTree3.ini are prior local runtime artifacts; their schemas are observed, but no behavior was observed live.
- Ghidra's full auto-analysis exceeded the default 330 s deadline. A reduced-analyzer profile (disabled: Decompiler Switch Analysis, Decompiler Parameter ID, Function ID) completed both snapshots: Geek **16,776 procedures / 4,439 defined strings**, WizTree **35,969 procedures / 14,454 defined strings**. Targeted pseudocode was extracted for both. All pseudocode is decompiler reconstruction, not original source.
- The `.po` source line references are compiler/shipped localization metadata, not recovered source. They establish feature area, not exact control flow.
- Remaining unresolved internals: exact `WhichItemBetter` ranking; exact Levenshtein scoring in install-location inference; WizTree hardlink policy and sparse/compressed accounting details; CSV/TSV import schema edge cases; treemap layout arithmetic. These are not claimed as observed behavior. The WizTree `.MFT` footer layout is now observed: raw MFT records followed by `VOLDATA2`, a 0x60-byte `NTFS_VOLUME_DATA_BUFFER`, and a one-byte drive letter.
- WizTree3.ini is version-3 runtime evidence and must not be presented as 4.33 defaults.
- Geek's `getRunningProcessesStartedAfter` call site and `CScannerCustomRules` rule source remain unknown pending decompilation.
- PurgeKit is an independent implementation; no GPL or proprietary code was copied. Findings are behavioral/architectural.

## 6. Recommended parity roadmap

**Completed earlier (2026-10-26):** derived-field view parity (Attributes, Share %, duplicate Count/Waste), Name+Size+Date duplicate mode, name-vs-path file filtering, configurable max-file limit, fuzzy install-location inference, Start Menu shortcut fallback for leftovers, Windows Job Object process-tree wait, and MFT fast-path scanning for selected folders.

**Completed in this iteration (2026-10-27):**
1. Geek-style derived-field cache for install location, resolved icon, size and signature status, with file/registry fingerprinting and a Settings Clear cache action. Measured warm registry refresh: 1.01 s → 13.8 ms for 56 apps on this host.
2. WizTree/PurgeKit CSV import (comma, tab, semicolon), path/size/date/attribute parsing, tree reconstruction, searchable index, and read-only safety. Imported snapshots cannot be quarantined.
3. Full-file CSV export, path include/exclude filters, persistent disk view preferences, and elevated restart.
4. Multi-root scans (semicolon-separated targets) with nested-target deduplication, merged tree, cross-root duplicate detection, per-volume accounting and protected scan roots.
5. Auto/Light/Dark themes with pre-hydration palette selection, Windows theme following and native title-bar sync.
6. Versioned gzip `.pkmft` dumps of the full FlatNode tree with volume metadata, dump listing and read-only reload without Administrator.
7. Color-blind palette for semantic status colors, file-type colors and treemap folders.
8. Expanded icon pipeline: environment-expanded DisplayIcon, Start Menu shortcut IconLocation/target, portable/CLI/toolchain sources, UWP manifest executable and bounded package walk, WindowsApps-only shell fallback for stub packages. Host coverage is 132/133 inventory rows.
9. English/Vietnamese i18n infrastructure (English default), WizTree-style treemap label/weight/free-space/small-file controls, printable disk HTML report, and bulk uninstall failure reporting.

**Completed in this iteration (2026-10-28):**
1. WizTree export parity: CSV/TSV output, current-view vs all-matches scope, optional per-folder direct totals and created/last-accessed columns; WizTree’s own export dialog strings (`Export Files`, `Export Folders`, `percentage of parent`, `Last Accessed`, `MFT record number`) were confirmed from the shipped English locale.
2. Geek-style install-date fallback: normalize `InstallDate`, infer from the install folder or uninstaller creation time when absent, persist it in the derived cache, and show it in the app row, preflight card and reports. Host coverage: 137/138 inventory rows (registry, Store, CLI, toolchain and portable paths).
3. Treemap navigation: double-click zooms a file into its parent folder and an explicit Up control plus breadcrumbs walk back out.
4. Project Sweeper deletion is bound to the last scan result, so only scanned folders can be removed.
5. Export completion: parent-percent, MFT-record and drive-size options, plus a full file-types CSV export; MFT record numbers are carried through the index and `.pkmft` dumps.
6. WizTree `.MFT` import: Ghidra decompilation of the dump flow (`0xb7c240`) and writer (`0x84e780`) showed raw MFT records followed by an 8-byte `VOLDATA2` magic, a 0x60-byte `NTFS_VOLUME_DATA_BUFFER`, and a one-byte drive letter. The loader reads both plain raw dumps and this footer, populates volume size/drive, and is read-only. It loaded a 13,402,112-byte raw MFT sample (10,854 files / 978 directories) end-to-end.

**Remaining / deliberately out of scope:**
1. Live elevated validation of folder-MFT scans, WizTree-generated `.MFT` dumping, and multi-process uninstaller waits requires an Administrator session.
2. Provisioned UWP packages are deliberately excluded: enumeration requires elevation and removing them changes provisioning for future users; Geek’s shipped strings do not expose a provisioned-package UI. Metro/custom rule scans likewise have no evidence-backed user-facing contract.
